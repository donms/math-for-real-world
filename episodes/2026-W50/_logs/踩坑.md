## 坑 1 ★★★ 落盘时机与超时风险不匹配 => **静默丢失 73% 的数据**

### 症状

第一版声明级抽取扫完了全程：

| 项 | 内存里 | 落盘 |
|---|---|---|
| `.lean` 扫过 | **115894 个** | — |
| 读取 | **2016.7 MB** | — |
| 模块 | **115894** | **只有 29951** |
| 声明 | **theorem 1101212 / lemma 1342346 = 244 万条** | 661863 条 |

**日志还写着「已落盘 29951 个模块」，看起来像是正常完成。**

### 根因

脚本只在**两个时刻**写文件：

1. `except` 分支（捕获超时）；
2. **循环正常结束后**。

而第 2 处要**一次性序列化十几万个模块**的 JSON，**耗时几十秒** ——
**网络超时恰好发生在这个窗口内**。

更迷惑的是：日志那句「已落盘 …」来自**异常分支**，
用的是**上一次崩溃时的旧计数**，所以数字看起来是"合理的部分结果"。

### 修法

改为**边抽边 `append`**：

```python
pending = []
if len(pending) >= 1500:
    with OUT.open("a", encoding="utf-8") as fa:
        for k in pending:
            fa.write(json.dumps(done[k], ensure_ascii=False) + "\n")
    pending.clear()
```

**效果**：修完后**同样 5 次超时中断**，
落盘从 29951 涨到 **41272**，**一行没丢**。

### ★ 通用教训

> **长任务的落盘时机必须与超时风险匹配。**
> 「结束时统一写」在大数据量下**等于不写** ——
> 因为**最可能中断的时刻，正是最需要写的时刻**。

**判据**：如果一个任务的"最后一步"是输出结果，
而输出量随处理量增长 —— **那它不是最后一步，是随时都该做的事**。

## 坑 2 ★★ 顺序流的"尾部覆盖"问题

### 症状

`tar.gz` 是**顺序流**，中断后重试**必须从头扫**。
=> **越靠后的模块越抽不到**。

而 `UniqueGames`（本期的头条证据）恰好在中后段：

$$
\text{覆盖率} = \frac{1}{479} = \mathbf{0.2\%}
$$

**头条证据的核心部分，恰好没抓到。**

### 修法

**弃 tar 流，改用"已知模块名 → 算文件路径 → 定向取"**：

```python
path = mod.replace(".", "/") + ".lean"
url = f"https://raw.githubusercontent.com/openai/math/main/{path}"
```

**关键洞察**：我已经有 `imports.jsonl`，**它就是那份"文件清单"** ——
**不需要再调 API 列目录**。

**效果**：**479/479，零失败**。

### ★ 通用教训

> **顺序流的重试成本是"从头再来"，所以尾部数据天然吃亏。**
> 若有**随机访问**的替代路径（按名字取），**优先用它补齐尾部**。

**另**：初版我试图用 git trees **递归 API** 列目录，
**跑了 21.7 分钟只占 29 MB** —— 那个响应本身大到会 `IncompleteRead`。
**"先列清单再取"不如"直接按规则算路径"。**

## 坑 3 ★★ 模块名前缀口径不一致 => **两次算出全 0**

### 症状

`q5_ug_focus.py` 算出的**入度、分层全是 0**，
但 `拓扑访问 479/479` 显示图是完整的。

### 根因

**三个文件里的模块名写法不同**：

| 文件 | 模块名 |
|---|---|
| `imports.jsonl` | `lean.OAI.Computability.UniqueGames.Theorem`（带前缀）|
| `decls_uniquegames.jsonl` | 定向取数时我**也加了**前缀 |
| 但 `q5` 脚本里**先去掉了一边的前缀** | => 两边对不上 => `m not in nodes` 恒真 |

**第一次修**：给 import 侧去前缀（但声明侧仍带）=> 还是 0。
**第二次修**：**两侧都去前缀** => 才对。

### ★ 通用教训

> **跨数据源传递"名字"时，必须先对齐口径**，
> 而且这类错误**不抛异常，只给出全 0 或全错的结果**。

**防御**：给这类结果加**断言** ——
**"入度全 0"太整齐了，不像真的**，应该直接报错。

## 坑 4 ★ 抖音卡片 `--out` 相对路径基准错

### 症状

```
共渲染 6 张卡片 → .\episodes\2026-W50\视频\素材9x16
```

落到 **`episodes/2026-W50/视频/`**，而不是 **`publish/视频/`**。

### 根因

`render_cards.py --out` 是**相对清单所在目录**解析的
（清单在 `publish/`，所以 `--out "视频/素材9x16"` 落到期目录）。

**这正是 skill 4.2.1 第 5 条记过的坑** —— 我又踩了一次。

### 修法

渲完**检查真实落点**（不是看 stdout 的路径），
用 `Get-ChildItem -Recurse` 找到实际位置再搬。

**并且**：`--ep` 模式下 `img` 路径基准是**期目录**，
用错基准会让"缺图"检查给出**假阳性**（我这次也遇到了：
按仓库根解析报 25 张缺图，按期目录解析是 0 张）。

## 坑 6 ★ 字数口径：平台的"字数"是**字符数**，不是汉字数

### 症状

B站简介我按"汉字数"砍到 286 字，自以为满足 200–400，
而 `publish_check` 报 **455 字，超限**。

### 根因

`count_cjk` 的口径是 **去掉空白后的全部字符数**（含标点、数字、ASCII、URL）。
**标点能占中文正文的 25–34%**，而一条 URL 就占 45 字符。

**=> 按"汉字数"估会系统性偏小 30%+。**

### 修法

用 `re.sub(r"\s", "", text)` 的长度当判据；
并且**正文里不放长 URL**（挪到置顶评论）。

**最终**：B站正文 **387 字符**（要求 200–400）[OK]

### ★ 通用教训

> **凡是"字数限制"，先确认口径**（汉字 / 字符 / 是否含标点）。
