# W55 · 结果 03：Python ↔ HTML 双版本一致性校验

> **为什么要单独出一份文档**
>
> 用户最初选的是 **C 方案：Python 仿真 + HTML 交互**。
> **两套实现最大的风险是"公式悄悄走样"** —— 网页看起来在跑，数字却是错的。
>
> **⇒ 必须有可复现的对账记录，不能只说"我检查过了"**。

## 1. 校验方法

### 1.1 ★ 校验的是"网页真正会跑的那份代码"

```
Node.js + DOM 桩
   ↓ 读取 publish/sim.html
   ↓ 抽出 <script> 块
   ↓ 执行（document/window/canvas 全部打桩）
   ↓ 读它算出的 window.__SIM__()
   ↓ 与 Python 的 run_mission10_auto() 逐项对比
```

**关键**：不是"另写一份 JS 来对比"，而是**把网页里的脚本原样跑起来**。
若网页脚本被改坏，校验立刻失败。

脚本：`scripts/verify_html_node.js`（Node 侧）+ `scripts/verify_dual.py`（对账）。

### 1.2 判据：**相对 5% 或 绝对容差**

$$\text{通过} \iff \left(\frac{|a-b|}{|a|} \le 5\%\right)
\ \text{或}\ \left(|a-b| \le \text{atol}\right)$$

> **⚠ 为什么必须带绝对容差**
>
> 落地 $v_z$ 两边分别是 $-0.065$ 与 $-0.020$，
> **都远小于 $-0.5$ 的目标值**（都是"非常软的着陆"）。
> 相对差 **69%**，但绝对差只有 **0.045 m/s**。
>
> $$\boxed{\text{近零量的相对误差没有意义}}$$
>
> 只按相对差判，会把两个一致的实现判成不一致 —— **那是指标选错了，不是实现错了**。

## 3. ★ 移植过程中抓到的三个真 bug

### 3.1 `tTrig` 取错了时刻

**错**：取"进入缓冲阶段的时刻"
**对**：取"下降穿过触发高度的时刻"

**后果**：探路那遍（不滚转）里相位立刻跳到 `buffer`
⇒ **滚转窗只剩 0.2 s ⇒ 角加速度爆炸、共转 1120°**。

### 3.2 触地判据卡在浮点数边界

**现象**：推力在 $z \approx 0$ 处"开—关—开"振荡，
$z$ 永远停在 $+10^{-6}$，**进不了制动阶段**。

**后果**：落地被推迟到 6.15 s，**车在原地悬停 2.8 s**。

**修法**：触地容差取 **20 mm**（≈ 悬架行程，物理上就是"轮胎接触地面"）。

$$\boxed{\text{"贴地"必须在状态机里显式建模，不能靠坐标巧合}}$$

### 3.3 缓冲推力冻结后一直施加

**现象**：车停止下降后推力仍在推 ⇒ **反向飘走**
（峰值涨到 37.5 m、11 s 不落地）。

**修法**：只在 $v_z < 0$（仍在下降）时施加 —— **缓冲是刹车，刹住就松。**

## 4. 3D 视图

### 4.1 做法：Canvas 2D 手写渲染器，**零外部依赖**

**为什么不用 three.js**：单文件、离线可用是底线；
引入 CDN 离线就废，内联则 600 KB 以上。

**四步渲染**：

1. 相机基 $\hat f=\dfrac{t-e}{\|t-e\|}$，$\hat r=\dfrac{\hat f\times u}{\|\cdot\|}$，$\hat u=\hat r\times\hat f$；
2. 透视 $s=f/z$，屏幕点 $=(c_x+xs,\;c_y-ys)$；
3. **背面剔除**：$\hat n\cdot(\text{相机方向}) \le 0$ 即剔除；
4. Lambert 着色 $\max(0,\hat n\cdot\hat L)$。

**⇒ 车身 14 面 + 四轮 96 面 + 障碍 30 面，60 fps 无压力。**

### 4.2 ★ 为什么必须做背面剔除

车身由"放样带 + 两块侧盖板"组成时，**侧盖板不是平面**（半宽随高度变化），
其**面心深度与放样带几乎相同** ⇒ 画家算法排序随机 ⇒
盖板被画到带子下面 ⇒ **车身变成"镂空条纹壳"**。

$$\boxed{\text{凸体只需画正面，排序问题根本不存在}}$$

**前提**：法向必须朝外，故先用"部件中心 → 面心"校正：

$$\text{若 }\hat n\cdot(\mathbf m-\mathbf c)<0 \ \Rightarrow\ \hat n:=-\hat n$$

### 4.3 渲染可执行性验证

沙箱里**起不了浏览器**（Edge 的 crashpad 与网络沙箱被拒，试过三种方式后停止）。
**⇒ 改用 Node 打桩执行**：

| 检查 | 结果 |
|---|---|
| `requestAnimationFrame` 回调 | 7 次 |
| canvas `fill` 调用 | **301** |
| canvas `stroke` 调用 | **399** |
| `#err` 内容 | **空**（无异常） |
| 判定 | **✓ 3D 渲染跑通** |

### 4.4 ★★★ 相机"上"向量用错 ⇒ 整个世界侧翻 90°（用户发现）

**用户反馈**：**"网页版的 3D 效果相机视角不对，感觉地在天上。"**

**完全正确，这是我的错误。**

本工程的世界坐标是 **$z$ 向上**（$x$ 前进、$y$ 左右、$z$ 高度）。
但相机基写成了：

```js
const cam = makeCam(eye, tgt, [0, 1, 0]);   // ← 错！这是"左右"轴
```

**后果**：$\hat r=\dfrac{\hat f\times(0,1,0)}{\|\cdot\|}$ 落在 $x$–$z$ 平面，
而 $\hat u=\hat r\times\hat f$ 的**主要分量变成 $\pm\hat y$** ——
**屏幕竖直方向成了世界"左右轴"** ⇒ **整个世界侧翻 90°，地面跑到画面上方。**

$$\boxed{\text{相机的 "up" 必须是世界的"上"，不是随便一个垂直方向}}$$

**修法**：`up = (0,0,1)`。**Python 预览里同一处也错了，一并修正。**

### 4.5 ★ 地面必须"铺面"，且不能依赖多边形是否在视锥内

**现象**：障碍物像**浮在空中**，没有地平线。

**两次失败的尝试**：

| 尝试 | 失败原因 |
|---|---|
| 大四边形（86×52 m）| 角点在相机背后 ⇒ `project()` 返回 `null` ⇒ **整块跳过** |
| 缩小四边形 | 仍可能有一角越界；且配色与背景太近 |

**最终做法：算地平线，在屏幕空间填线下区域**

$$\hat f_h=\frac{(f_x,f_y,0)}{\|\cdot\|},\qquad
p_h=\operatorname{proj}\left(\mathbf e+900\hat f_h\right)$$

**在 $y > p_h$ 的区域填一条竖直渐变带。**

$$\boxed{\text{不依赖任何多边形顶点是否在视锥内 ⇒ 永远不会失败}}$$

### 4.6 ★ 轮心多加一次 `BODY_LIFT` ⇒ 轮子跑到车顶上（用户发现）

**用户反馈**：**"轮子跑车顶上去了。"**

**完全正确。**

`CAR_PARTS` 里所有部件的 `oz` 都是**相对质心**的（质心离地 `BODY_LIFT = 0.60`）。
轮子那行却把 `RW` 当成了"离地高度"：

```js
const [cyw, czw0] = rot(wy, RW);      // RW = 0.36 当成离地高度
const cwz = z0 + BODY_LIFT + czw0;    // 又加 0.60
```

$$\Rightarrow\quad z_{\text{轮心}} = 0.60 + 0.36 = 0.96\ \text{m}$$

而**车顶在** $0.60 + 0.27 = 0.87$ m ⇒ **轮心比车顶高 0.09 m**。

**正确**（与 `CAR_PARTS` 同约定）：

$$z_{\text{轮心相对质心}} = R - \text{BODY\_LIFT} = -0.24
\;\Longrightarrow\; z = 0.60 - 0.24 = 0.36 = R\ \checkmark$$

**⇒ 轮底恰好擦地。**

### 4.7 ★★★ 四个 bug 的共同根因：**坐标约定不统一**

| # | bug | 表现 |
|---|---|---|
| 1 | `tTrig` 取"进入阶段"而非"穿过高度" | 共转 1120° |
| 2 | 触地判据 `z<=0` 卡浮点边界 | 原地悬停 2.8 s |
| 3 | 相机 up 用错轴 | 地面在天上 |
| 4 | 轮心多叠 `BODY_LIFT` | 轮子在车顶 |

$$\boxed{\text{同一场景里同时存在三套坐标：世界系、车体系、相对质心系}}$$

**只要有一处混用，就会出现"看起来不可能"的错位。**

**⇒ 防错的做法：每个坐标系的量都写清"相对谁"**，
例如 `oz_center` / `z_world` / `y_body`，而不是统统叫 `z`。

### 4.8 ★ 只旋转"中心"、不旋转"几何" ⇒ 车身与车轮各转各的（用户发现）

**用户反馈**：**"在滚转的时候车轮和车身不固定在一起。"**

**完全正确，而且比"车轮"更严重：车身盒子本身也没转。**

#### 错在哪

`carFaces` 对每个部件先算旋转后的中心：

```js
const [cy, cz] = rot(oy, oz);
const F = boxFaces(cx0, cy, cz0, Lx, Wx, Hx);   // ← 盒子仍轴对齐
```

`boxFaces` 内部：

```js
P8[...] = [cx + sx*hx, cy + sy*hy, cz + sz*hz];  // ← 局部尺寸没旋转
```

$$\boxed{\text{旋转的只是"位置"，几何仍与世界轴对齐}
\ \Rightarrow\ \text{看起来是"盒子在滑移"，不是"车身在翻滚"}}$$

**车轮同理**：轮心跟着转了，但**轮盘自身的局部偏移 $(d_x,d_z)$ 没转**，
而轮轴又固定沿世界 $y$ ⇒ **轮子与车身各转各的**。

#### 修法

**局部偏移也必须过同一个旋转**：

$$\begin{pmatrix}y'\\z'\end{pmatrix}
=\begin{pmatrix}\cos\theta&-\sin\theta\\ \sin\theta&\cos\theta\end{pmatrix}
\begin{pmatrix}s_y h_y\\ s_z h_z\end{pmatrix}$$

* `boxFaces` 增加 `roll` 参数（车体传 $\theta$，障碍物传 0）；
* 车轮环的偏移按 $\theta$ 旋转（轮轴不再固定沿世界 $y$）。

#### ★ 这是"同一类错的第二次"

**我在 matplotlib 版 `sim_anim3d_v2.py` 的 `box_faces` 里已经踩过"双重旋转"**
（`double rotation`），拷到 JS 时**又漏了同一处**，只是方向相反：
那次是**转了两次**，这次是**一次都没转**。

$$\boxed{\text{坐标变换的错永远成对出现：要么漏转，要么多转}}$$

**⇒ 唯一可靠的检查方式：把姿态设成 90°，肉眼看几何是否真的翻转**
（0°/17° 时漏转和多转都看不出来）。

## 5. 边界与诚实性

1. **★ 校验覆盖的是物理量，不是像素** ——
   布局、配色、动画流畅度需要人眼确认，机器校验不了。
2. **★ 浏览器截图缺失** —— 沙箱限制，已在 §4.3 说明替代验证方式。
3. **★ 两版本步长不同**，因此存在 1~2% 的系统偏差；
   **若要完全一致，需在 JS 里实现 RK4**，但交互流畅度会下降。
4. **★ 3D 视图是"技术示意"级别**，不是渲染级拟真：
   车身是无曲面的多凸块，靠**青色顶面**作为姿态参照。
