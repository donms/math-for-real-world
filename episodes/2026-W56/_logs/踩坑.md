> **物理量纲的符号与单位**、**从"能算"滑向"能测"的偷换**。
> 下面每条都给出"症状 / 根因 / 防线"。

## W56-1 ★★★ 加速度符号：一次符号错让 SVM 峰从 4.9 g 变成 1.58 g

**症状**：`sig_fall.py --selftest` 报

```
[X] ⑮ IMU SVM 峰 1.58 g（题设 3–10）
```

而模型的冲击减速度明明是 4.0 g。

**根因**：我把冲击段写成 `a = -A_imp·sin(...)`，即"向下"。
但一次摔倒的冲击是**减速**：速度从 −1.4 m/s 回到 0，所以

$$\frac{dv}{dt}>0\ \Rightarrow\ \text{加速度向上}$$

于是 SVM $=1+a_{\text{kin}}/g$ 拿到的是**下落段的 +0.58 g**，不是冲击的 +3.9 g。

**修法**：`a = +A_imp·sin(...)`；并把 `acc_up = a/G`（原来写成 `-a/G`）。

**防线**：断言 ⑮ 直接拿**题设的物理区间**（3–10 g）当判据，
不用"看起来对"当判据。

> ★ **教训：符号错时，所有数字都"看起来对"。**
> 只有拿题设的物理区间当断言，才能把它逼出来。

## W56-2 ★★★ 制动比 β 的估计量系统性虚高 0.14

**症状**：自检 ⑪ 报 `sit_fast: β 实现 0.593 对标称 0.45`。

**根因**：我用"加速度峰值之前 30 ms 的速度"当 $v_{\text{触地}}$。
但半正弦脉冲的峰在脉冲**中间**：

$$a(t)=A\sin\tfrac{\pi t}{T}\ \Rightarrow\ v(t)=v_{\text{end}}
\Big[1-\tfrac12\big(1-\cos\tfrac{\pi t}{T}\big)\Big]$$

在 $t=T/2$（加速度峰）处，$v=v_{\text{end}}/2$。取那一点，等于把
"已经减速了一半"的速度当成触地速度。

**修法**：用解析结论

$$\boxed{v_{\text{end}}=2\,v(t_{a\text{-峰}})}$$

改完之后真值侧无偏（自检 ⑪：0.299 / 0.453 / 0.700 / 0.551 / 0.600）。

**但修好之后仍然把通道删了**：加噪声后估计量标准差 0.22–0.42，
类间差只有 0.15。

> ★ **教训：修好一个估计量，不等于救活一个通道。**
> 判据是"加噪声后还剩多少信噪比"，不是"真值侧是否无偏"。

## W56-3 ★★★ "算得出"被偷换成"测得到"

**症状**：初版每个传感器都有 $v,\beta,a,h,\theta$ 五个特征。
蒙特卡洛一跑，摄像头的 $a$ 通道：摔倒 0.86 g、躺沙发 0.64 g，
标准差 0.12。**几乎不携带信息，但表上看着像"有"。**

**根因**：`extract()` 对所有传感都算同一套特征，
没区分"这个传感物理上能不能测这一维"。

**修法**：加一张**能力矩阵** `CHANNELS`，不在表里的通道一律置 `None`：

```python
CHANNELS = {
    "camera": ("v", "h", "th"),      # 冲击与制动比都删了
    "mmwave": ("v", "a", "h"),
    "wifi":   ("v",),
    "ble":    ("rssi",),
    "lidar":  ("v", "h", "th"),
    "imu":    ("v", "a", "th"),
}
```

并在 `extract()` 末尾统一置空：

```python
for k in list(out):
    if k != "beta_diag" and k not in CHANNELS[name]:
        out[k] = None
```

> ★ **教训：一张"能力表"必须显式存在，否则"能算"会自动变成"能测"。**
> 这是本期最容易骗过自己的一处。

## W56-4 ★★ 多普勒谱的 y 轴是错的，因为基带采样率不够

**症状**：毫米波谱图的 y 轴只到 ±50 Hz，而正文写着"摔倒特征在 1 kHz"。

**根因**：复基带是在 **100 Hz** 的测速帧率上生成的，Nyquist 只有 50 Hz。
1 kHz 的多普勒直接混叠掉了。

**修法**：谱图另按 **4 kHz** 重算复基带（Nyquist 2 kHz），
测速仍用 100 Hz 的包络。**两件事的采样率要求差 40 倍，不能共用一条时间轴。**

**防线**：`_stft` 的 `f` 轴与 `Z` 的转置必须对齐；
`pcolormesh` 的 `C` 维度是 `(len(f), len(t))`，我第一版写成 `(len(t), len(f))`，
抛 `Dimensions of C should be one smaller than X and Y`。

> ★ **教训：一张图有两套采样率时，必须在代码里显式分开，不能"顺手复用"。**

## W56-5 ★★ 类内变异只保正不封顶，把数组算爆 18 GiB

**症状**：

```
numpy.core._exceptions._ArrayMemoryError:
Unable to allocate 18.4 GiB for an array with shape (64, 19283166)
```

**根因**：类内抖动写成 `p[k] = max(1e-6, p[k] * (1 + 0.22*jitter*N))`。
**只保正、不封顶。** 于是某个实现里 $v_{pk}$ 被压到 1e-6，
而下降段时长是

$$T_d=\frac{\Delta h}{v_{pk}\bar{\tilde v}}$$

⇒ 反解出**上万秒**。

**修法**：乘子**双向截断**到 $[0.35,1.8]$，并加断言 `t_desc < 5.0`。

> ★ **教训：凡"乘一个随机因子"的正值参数，都要问"它会不会趋近 0"。趋近 0 的参数一旦进分母，就是内存炸弹出场的地方。**

## W56-6 ★★ `$rho_{FA}$ 在高门限下退化成全 1.00`

**症状**：相关组矩阵一度变成"摄像头/激光雷达/可穿戴/毫米波之间全是 1.00"，
而正确的值是 0.18–0.97。

**根因**：$\rho_{FA}$ 用重叠系数算，而重叠系数依赖**各类负样本在误报里的份额**。
当门限被"未知活动"顶到 5.5σ 时，所有**已知**负样本的份额都趋于 $10^{-8}$ 量级，
归一化之后只剩"$\mu$ 最大的那一个"，两类都落到同一个类上 ⇒ 伪相关 1.00。

**修法**：$\rho_{FA}$ 固定在**参考门限**上算（只用已知负样本求出的那个门限），
并在 `rho_fa_pair` 里默认 `tau=None` 就走参考门限。

> ★ **教训：凡是"归一化后的份额"，都要问"分母趋于 0 时它变成什么"。这类退化不报错，只给出一个很好看的 1.00。**

## W56-7 ★★ 主表全是 100%，需要并排给"上界 vs 工程实际"

**症状**：只算 6 类已知负样本时，激光雷达与摄像头都是 100.0%。
两个 100% 放一起，读者会以为模型没跑对。

**根因**：不是 bug，是**负样本表太干净**。真实误报主要来自未建模的活动。

**修法**：主表保留（标"上界"），并排加一列"加 60 次/天未知活动"的工程实际值
（100.0% → 79.1% / 67.6%）。同时给 $N_u\times r$ 的六格边界表。

> ★ **教训：模型的"高准确率"往往说明负样本集不完备，不说明模型好。这时该补的是负样本，不是补一列"看起来合理"的噪声。**

## W56-8 ★★ AND 融合给了弱的一方"否决权"，这一点不好直觉

**症状**：激光雷达 + WiFi 的融合检出 62.3%，**低于激光雷达单独的 79.1%**。

**根因**：AND 要求两票。WiFi 的 $d'=1.19$，它在门限之上"报"的概率远低于
激光雷达，于是**它能否决激光雷达的每一次正确报警**。

**修法**：不改模型（这是正确的物理），改**结论的写法**：

$$\boxed{\text{融合的先决条件是"两路各自都够好"，相关性只决定在此之上还能多赚多少}}$$

并把这句放进 `q4` 的标题位置。

> ★ **教训：一个反直觉的结果，先怀疑模型，再怀疑直觉。这次检查后发现模型是对的（AND 的定义就是"都报"），错的是"加了就更好"的直觉。**

## W56-9 ★ PowerShell 的 `@"..."@` 会吃掉补丁脚本里的引号

**症状**：用 here-string 往 Python 脚本里打补丁，写进去的是

```python
GATE_BY_SCEN = {bedroom: 5.0, nh: 20.0}      # 引号没了
```

直接把脚本写坏（`NameError: name 'bedroom' is not defined`）。

**根因**：`@"..."@` 是**可展开**的 here-string，内部的 `\"` 会被处理掉。

**修法**：补丁脚本先 `Set-Content -Encoding UTF8` 落成 `.py` 再执行，
或者干脆用 `edit` 工具做精确替换。**不要在命令行里内联多行 Python 补丁。**

> ★ **教训：与 skill 里"写文件用 write 工具、不要用 here-string"是同一个坑，这次踩的是它的变体（用 here-string 生成补丁脚本）。**

## W56-10 ★ 自检的判据要拿"题设区间"，不要拿"上一版输出"

**本期做对的一处**：断言 ⑮ 用题设的 `3 < SVM 峰 < 8`，
所以符号错当场被抓住；若判据写成"和上一次运行一致"，错了也发现不了。

**本期做错的一处（已改）**：断言 ⑥ 最初写成 `pr_bad["d"] < 0`，
而 Fisher 投影**总把正类放在负样本之上**，`d` 恒为正 ⇒ 断言恒假。
改成"负样本比正类还高分时检出率被压到 2% 以下"，才是真的结构性失效。

> ★ **教训：断言要表达"物理上必须成立的事"，不是"我上一次算出来的数"。前者会抓到错，后者只会锁死错。**

## W56-11 ★★★ 封面的大数字块永远是空的：三道闸门各漏一次

**症状**：B站封面只有标题与副标题，`big`（−9.7 点）与 `big_label`
**根本没画**，而抖音/小红书封面有。

**根因**：`big` / `big_label` 要走**三道**闸门才能到渲染器，三道都漏：

| # | 位置 | 原来的字段列表 |
|---|---|---|
| 1 | `make_storyboard.FIELDS["cover"]` | 白名单里没有 `big`，**加了反而会报错退出** |
| 2 | `make_storyboard` 的 `sc[k] = lay[k]` 循环 | `("title","sub","tag","lines","rows","note","cta")` |
| 3 | `make_render_specs.slides()` | 同上，也没有 `big` |

而 `render_slides16x9.slide_cover` **一直在读这三个字段** ⇒ 读不到就画空，
`if spec.get("big")` 静默跳过，**没有任何输出**。

**修法**：三处都补 `big` / `big_label`（第 1 处必须同时加进白名单，否则抛错）。

> ★ **教训：一个字段要穿过 N 层才能上屏，就在 N 层都断言它到得了。
> 只在最后一层读、不在前面几层带，是最常见的"少了一半内容还不报错"。**

## W56-12 ★★★ 抖音的图卡是空卡：`figure` 分支丢 `img`

**症状**：抖音第 4 屏是"WiFi 眼里：坐下和摔倒一样"的图卡，实际渲出来
**只有标题没有图**。

**根因**：`make_render_specs._douyin_cards()` 里只有 `cover` 与 `compare`
两个分支会带额外字段，`figure` 落到 `else`，只拿到 `lines`。
而 `render_cards.draw_figure` **在 `img` 缺失时不报错**，只是画一个缺图框之外的空卡。

**修法**：`figure` 分支透传 `img` / `note`。

> ★ **教训：把"卡片种类"当成一个 if/elif 链时，每加一种 kind
> 都要问一句"它的必填字段谁来带"。兜底分支通常只带一个字段。**

## W56-13 ★★ 抖音口播代码块必须**空行分段**，否则 7 屏念同一句

**症状**：`make_render_specs` 报抖音 **7 屏 453.5 秒**（应为 65 秒）。

**根因**：`_douyin_cards()` 用 `re.split(r"\n\s*\n", body)` 切段
⇒ **只有空行才算分段**。我生成 `内容/抖音.md` 时把 7 段用**单换行**连写
⇒ 切出 **1 段** ⇒ 第 2 屏起 `chunk = []` ⇒ 兜底 `txt = dy_paras[-1]`
⇒ **7 屏全念同一段 309 字**，总时长 7 × 64.8 s。
**全程不报错**（W54-2 是"段数少于屏数会重复最后一段"，这次连报都没报，
因为段数 = 1 也满足"每屏都有文本"）。

**防线**：
1. 生成器里 `"\n\n".join(...)`，并在出口**断言段数 == 屏数**；
2. 看 `make_render_specs` 打印的**总时长**：抖音 7 屏 ≈ 50 秒，
   出现三位数秒就是这里出了问题。

> ★ **教训：W54 已经记过一次"段数对不上"，本次是它的变体 ——
> 判据不能只看"每屏有文本"，要看"每屏的文本是不是同一段"。**
> 最便宜的判据是**总时长**：它一异常就会跳出来。

## W56-14 ★★ `fig.set_dpi()` 会改画布像素尺寸 ⇒ ffmpeg 静默丢帧

**症状**：动画渲染出 30 帧，ffprobe 只报 **8 帧 / 0.267 s**，
stderr 一行 `Invalid buffer size, packet size 5529600 < expected frame_size 6220800`。

**根因**：`figsize=(12.8, 7.2), dpi=150` 本来正好 1920×1080；
后面又调了 `fig.set_dpi(100)` ⇒ 画布变成 **1280×720**，
而 ffmpeg 按 1920×1080 收 ⇒ 每帧少 1/3 字节 ⇒ 解码器丢包。

**修法**：**画布尺寸从 canvas 读**，不要写死：

```python
W, H = (int(round(fig.get_figwidth() * fig.dpi)),
        int(round(fig.get_figheight() * fig.dpi)))
```

> ★ **教训：宽高是"派生量"，不是常量。凡是把派生量写成常量的地方，
> 一改参数就会错，而且错在**另一个进程**里（ffmpeg），报错信息不指向根因。**

## W56-15 ★★★ 把公式的**极值**当成了某个**点**的值（1.41× 对 1.30×）

**症状**：任务书写"摄像头×毫米波（ρ=0.18）的增益是 1.41×"。

**根因**：

$$\sqrt{\frac{2}{1+\rho}}:\quad \rho=0\Rightarrow1.414,\quad
\rho=0.18\Rightarrow1.302,\quad \rho=0.97\Rightarrow1.008$$

1.41× 是 **ρ=0（完全独立）的上限**，不是任何真实组合的值；
摄像头×毫米波是 **1.30×**（`q4` §8 原本就写对了）。

**处置**：正文写 1.30×，**并把 1.41× 作为 ρ=0 的参照线一起画进图里**
（曲线左端点 + 图例一行），两个数都出现、但各归各位。

> ★ **教训：报一个人的成绩，不能用班级最高分。
> 凡是"某个公式在某点的值"，先代进去算一遍，不要引用表格里相邻的那一行。**

## W56-17 ★ PowerShell 的 `Set-Content` 会把 UTF-8 脚本改成乱码

**症状**：用 `(Get-Content -Raw).Replace(...)` + `Set-Content -Encoding UTF8`

> ★ **教训：这是同一个坑的第二次变体。把它升格为"绝对规则"：
> 文件的写操作只走 write / edit 工具，shell 里只读不写。**
